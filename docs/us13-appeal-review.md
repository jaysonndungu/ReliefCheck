# US13 appeal review handoff

The `/appeal` screen accepts a selected disaster and one URL or appeal message. `POST /api/v1/appeals/review` accepts `{requestId, disasterId, input}` (maximum 4,000 characters) and returns `{requestId, snapshot, result, targets, citations}`. `result.status` is exactly `documented_official_channel`, `published_warning_found`, or `insufficient_evidence`; `reasonCodes`, per-target results, reviewed record summaries, and US04 citations explain the result. HTTP 503/409 errors are separate from a successful insufficient-evidence result. The additive schemas and route path live in `packages/contracts`.

Classification is deterministic. Submitted links are parsed with WHATWG URL/IDNA rules, never fetched. Host scope requires an exact normalized hostname; exact-URL scope preserves path and query and removes only the fragment. Credentials, unsupported schemes, IP literals, encoded hostnames, invalid percent escapes, and non-default ports fail closed. A bare hostname is accepted only when it is the entire input. Multiple links have an insufficient aggregate result; each parsed link retains its own evidence. Conflicting official and warning records produce **insufficient evidence** with both records visible, as required by the US13 request; this is deliberately stricter than the warning-priority row in `ai.md` §6. Unknown means unlisted, not fraudulent.

`AppealRegistryRepository` is an integration boundary for Anson's registry service and Jayson-coordinated publication schema. `lookup` must read one active snapshot plus reviewed campaign/warning versions, their selected-disaster membership, and approved evidence source membership and disaster tags consistently. `currentSnapshot` permits a final epoch check. The matcher also rejects non-reviewed, wrong-release, or wrong-disaster evidence and computes current channel eligibility at request time, capped at 30 days after review. Shared-platform records must be approved only with exact-URL scope. The production repository is currently absent and `apps/api/src/index.ts` passes `null`, so the endpoint returns `503 APPEAL_REVIEW_UNAVAILABLE`. No migration, draft publication, URL fetching, Gemini call, or US14 behavior is included.

Local checks: use Node 24.22.2, run `npm ci` if dependencies are absent, then `npm run build`, `npm run check`, and `npm run dataset:typecheck`. `npm start` serves `/appeal`; without `GET /api/v1/disasters`, it shows an explicit unavailable state. Synthetic API and browser-component tests in `apps/api/test/us13-appeals.test.ts` and `apps/web/test/appeals.test.tsx` cover the decision table. Live acceptance requires a published reviewed release for both events, a registry adapter, a working disaster endpoint, and human review of each cited claim and date.
